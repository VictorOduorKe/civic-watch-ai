CivicWatch AI Kenya — Milestone 8: Notifications

1. Objective

Implement the CivicWatch AI Kenya in-app notification system.

M8 should allow users to receive notifications generated by real platform events.

The notification system must integrate with the existing:

- M2 authentication
- M3 citizen dashboard
- M4 incident reporting
- M5 report tracking
- M6 OCL admin dashboard
- M7 incident management

At the end of M8, users should be able to:

1. Receive real in-app notifications.
2. See unread notification counts.
3. Open a notification list.
4. Mark individual notifications as read.
5. Mark all notifications as read.
6. Navigate from relevant notifications to the correct resource.
7. Receive report-related notifications based on actual database events.
8. Receive administrative assignment notifications.
9. Maintain notification history.
10. Prevent duplicate notifications.
11. Keep sensitive/internal information out of citizen notifications.
12. Preserve the existing secure cookie authentication architecture.

This milestone should establish a reusable notification service that later milestones can use for:

- Civic Alerts
- Civic Participation
- AI Assistant events
- other system notifications

Do not implement those future modules yet.

11. Entity Information

Use:

entity_type
entity_id
entity_reference

Example:

     ↓

12. Notification Deduplication

Notifications must not be duplicated when the same event is accidentally processed more than once.

Use:

dedupe_key

Examples:

report-received:25:7
status-change:25:103
report-update:25:51
assignment:25:18

The exact format can follow the implementation.

Create a unique constraint where appropriate.

---

13. Why Deduplication Matters

For example:

Admin changes status
       ↓
Database update succeeds
       ↓
Notification creation attempted
       ↓
Request accidentally retried
       ↓
Same notification attempted again

The user should not receive two identical notifications for one event.

17. Report Creation Transaction

Where appropriate, ensure the report and its notification do not create inconsistent state.

If the existing M4 report creation transaction is already structured, integrate the notification service into it carefully.

Possible approach:

BEGIN
    Create report
    Create attachment records
    COMMIT
       ↓
Create notification

If notifications are created after the main transaction, ensure a failed notification does not make the report appear failed.

The report itself must remain successfully created.

The system should log notification creation failure safely and allow controlled retry/recovery.

Do not roll back a valid citizen report simply because an in-app notification failed.

35. Read Fields

When a notification is marked read:

---

36. Idempotent Read Operations

Calling:

---

37. Notification Ownership

Every notification API must enforce ownership.

For example:

GET /api/notifications

returns only the authenticated user's notifications.

Never return:

WHERE is_read = ...

without filtering by authenticated recipient.

38. Critical Security Rule

Never trust:

from frontend requests.

Use:

req.user.id

or the equivalent authenticated identity established by M2.

63. Notification Failure

A notification failure should not corrupt the underlying business action.

Example:

Report successfully created
Notification insertion temporarily fails

The report must remain created.

Log the notification failure safely.

Do not expose infrastructure details to the user.

---

64. Retry Strategy

M8 does not need a queue system.

If notification creation fails:

- log the failure
- return the primary business operation successfully when appropriate
- make the failure observable during development

A future notification worker/queue can be added if the project requires it.

Do not introduce Redis/BullMQ just for M8.
