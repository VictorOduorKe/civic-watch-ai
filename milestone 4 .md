# CivicWatch AI Kenya — Milestone 4: Incident Reporting

## 1. Objective

Implement the **Incident Reporting module** for authenticated citizens.

At the end of this milestone, a citizen should be able to:

1. Open the "Report an Issue" feature from the citizen dashboard.
2. Select an incident category.
3. Enter incident details.
4. Provide location information.
5. Optionally provide GPS coordinates.
6. Upload permitted supporting files.
7. Choose whether the report should be treated as anonymous.
8. Choose a preferred contact method.
9. Submit the report securely.
10. Receive a unique CivicWatch report reference such as:

`CWK-2026-000001`

The report must be stored in MySQL and associated with the authenticated user.

Do NOT implement report tracking, admin review, assignment, notifications, AI verification, public maps, or civic alerts in this milestone.

# 7. Anonymous Reporting Design

Implement anonymous reporting carefully.

"Anonymous" should mean that the citizen's identity is **not presented as the reporter in normal report-facing views**.

However, the system may still retain the authenticated `user_id` internally for:

* abuse prevention
* account security
* duplicate prevention
* platform accountability
* future administrative workflows

Do not display the user's:

* name
* email
* phone number

as part of the anonymous report submission result.

Do not claim that anonymous reporting means the platform technically has no connection to the account.

If the UI explains anonymous reporting, use clear language.

Example:

> Anonymous reporting hides your identity from normal report-facing views. Your account may still be associated with the submission internally for platform security and abuse prevention.

Do not make legal claims about absolute anonymity.

### Security requirements

Do not trust the filename supplied by the browser.

Generate a secure/random stored filename.

Validate:

* file extension
* MIME type
* file size
* filename
* upload count

Do not allow executable files.

Do not allow uploaded files to be executed by the server.

Prevent:

* path traversal
* arbitrary filesystem writes
* executable uploads
* dangerous MIME spoofing
* unrestricted file sizes

Store uploads outside publicly accessible frontend assets.

For example:

```text

```

but make sure these files are not directly exposed through a public static route.

Do not create a public `/uploads` endpoint.

Set a reasonable maximum file size appropriate for the MVP.

Keep the limit configurable through environment configuration.

Example:

```env
MAX_REPORT_ATTACHMENT_SIZE_MB=5
MAX_REPORT_ATTACHMENTS=5
```

If the existing backend already has an environment configuration convention, follow it.

Do not hardcode secrets.

# 14. Report Creation Flow

The backend should perform approximately this sequence:

```text
Request
   ↓
Authentication
   ↓
Rate limiting
   ↓
Multipart/file validation
   ↓
Input validation
   ↓
Category validation
   ↓
Create report transaction
   ↓
Generate report reference
   ↓
Save attachment records
   ↓
Commit transaction
   ↓
Return safe response
```

If database creation fails, the transaction must roll back.

Do not leave orphan attachment records.

Do not leave partially created reports.

If uploaded files were stored before the database transaction successfully completed, clean up those files when appropriate.

# 30. Security Requirements

This milestone contains user-generated content, so security is important.

Implement or preserve:

### Authentication

Only authenticated users can submit reports.

### Authorization

User identity comes from authentication middleware.

### SQL Injection Protection

Use parameterized queries/prepared statements.

Never concatenate user input directly into SQL.

### XSS Protection

Treat title, description, location and other user input as untrusted.

Do not inject raw HTML.

### Input Validation

Validate on the backend.

### Rate Limiting

Apply an appropriate report-submission rate limit.

Do not allow a single account to flood the endpoint.

### File Security

Validate:

* size
* extension
* MIME type
* filename

Use generated filenames.

Never execute uploaded files.

### Path Traversal

Never construct storage paths directly from user-supplied filenames.

### CORS

Preserve the existing secure CORS configuration.

### Security Headers

Preserve Helmet configuration.

### Secrets

Never expose:

* JWT secret
* database password
* Gemini API key
* filesystem secrets

to the frontend.
